# Frontend handoff

The API uses `/api/v1`, bearer authentication for protected routes, JSON, and the shared error envelope in `API_CONTRACT.md`. Local interactive OpenAPI docs are at `/docs`.

The current orders API creates only pending order records. It does not charge payment, reserve stock, or fulfill. Use `Idempotency-Key` on order creation. A customer may cancel an unpaid `awaiting_payment` order with `POST /api/v1/orders/{id}/cancel` and a required reason; the backend applies no cancellation fee. Paid-order refunds and delivery-job cancellation rules remain undefined. Product and inventory schemas are available in OpenAPI: public products show only platform-published, in-stock items; merchant writes require organization ownership; new products are unpublished drafts. Do not assume fare values, payment success from redirects, GPS availability, or escrow semantics. Payment and KYB contracts remain incomplete.

Customer screens can use `PATCH /api/v1/users/me`, the `/api/v1/customers/me/addresses` address-book routes, and `/api/v1/customers/me/dashboard`. Checkout sends a caller-owned `delivery_address_id` to `POST /api/v1/orders`; the order snapshots that address and prices but remains unpaid and unfulfilled. Store screens can use `/api/v1/merchant/store-profile`, `/api/v1/merchant/dashboard`, and the public `/api/v1/marketplace/stores/{storefront_slug}` catalog. Platform management summaries are available at `/api/v1/admin/dashboard/summary`; operations can use the delivery-agent, shipment-assignment and operations-dashboard routes listed in `API_CONTRACT.md`. No live GPS, payment, or settlement routes are available yet.

The app can check `/api/v1/customers/me/verification-terms` and submit explicit acceptance to `/api/v1/customers/me/verification-terms/accept`. These routes return `configured: false` / 503 until management publishes and approves the final terms and privacy policy and configures their versions and URLs. Acceptance does not mean the customer has passed identity verification.

Organization settings and staff screens can use `PATCH /api/v1/organizations/{id}` and the member list/add/update/remove routes. Only owners can change roles or remove members; owners cannot remove or demote themselves through these routes.

Platform catalog moderation can use `GET /api/v1/admin/products/review-queue` with limit/offset pagination, then `POST /api/v1/admin/products/{id}/publish?organization_id=...` to approve an item. Rejection states and merchant-facing review notes are not modeled yet.

Rider and driver screens can use `/api/v1/delivery/agents/apply`, `/api/v1/delivery/me`, `/api/v1/delivery/me/availability`, `/api/v1/delivery/me/assignments`, `/api/v1/delivery/me/dashboard`, and assignment response/status-event routes. New agents start offline; agents must complete their name and phone profile, be activated by a platform admin, and set themselves online before dispatch can assign work. Assignment offers mark an agent busy; declining returns the agent online, and resolving the job returns the agent online. Platform dispatch screens can use `/api/v1/admin/delivery/agents`, `/api/v1/admin/shipments/{id}/assignments`, and `/api/v1/admin/operations/dashboard`, which includes availability counts. Role-specific event permissions are enforced. Delivery proof references are recorded but not verified; live GPS, document verification, notifications, and automated dispatch are not implemented.
